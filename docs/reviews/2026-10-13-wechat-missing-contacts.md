# 微信通讯录漏读修正（2026-10-13）

用户报告部分联系人按昵称、备注和微信号均无法找到。逐条核对当前账号的只读数据库，确认两条目标记录均存在于 contact 表，local_type=1、flag=1、delete_flag=0、verify_flag=0，但原读取规则强制要求 flag & 2，导致在进入界面前已经被丢弃。

已删除这一额外 flag 条件，按个人联系人类型读取，并继续排除本人、已删除记录、公众号、群聊和群成员缓存。保存到通讯录的群聊可能具有 local_type=1，因此额外按稳定 UserName 的 @chatroom 后缀排除，避免被误标为个人联系人。

初次总数 588 恰好与客户端数字一致，不能证明名单完整。修正后的当前本地快照读取 665 个唯一联系人，两条报告记录均能找到。其中一条用户提供的姓名与本地 nick_name 不一致，数据库保存不同昵称、空备注；通过微信号确认是同一记录，不推测或改写姓名。

同时修正文档中的类别描述：本机 local_type=5 的 67 条记录全部为 @openim 企业微信联系人，不能据此把 local_type=5 泛称为仅聊天好友。当前读取的是本地个人联系人记录，不能仅凭这些字段证明实时双向好友关系或与手机资料同步。

验证覆盖：

- Python 15 个用例通过：补充 flag=1、缺少 bit 2 的其他个人记录，以及 local_type=1 的已保存群聊/公众号排除。
- Java 定向 verify 的 17 个用例通过，覆盖昵称、备注、自定义微信号和稳定 UserName 的实际 JTable 搜索，以及原有助手协议、Excel 往返和国际化；打包和依赖声明分析通过。
- 用真实账号读取验证两条目标记录均被包含。最终 JAR 启动的实际通讯录表格有 665 行，分别输入用户报告的备注和微信号，两项搜索均返回 1 行。没有把账号、密钥、微信号或原始联系人记录写入项目文件。
