# Java 工具箱统一安全保险库设计

## 背景

Java 工具箱目前由两个功能保存敏感数据：账号密码管理器将记录写入工作目录下的 `toolbox-passwords.enc`，TOTP 工具则把包含 Base32 Secret 的完整账户 JSON 写入普通的 `toolbox-config.properties`。密码库使用单次 SHA-256 从主密码派生 128 位 AES 密钥，再以 AES-CBC 加密；该格式没有随机盐、可调工作因子或密文认证。配置和密码库都依赖应用启动目录，读写失败也缺少统一、可恢复的错误处理。

本设计是安全与可靠性升级路线的第一阶段，只处理统一保险库、配置路径及旧数据迁移。CI 全面建设、复杂面板拆分、通用日志体系、完整国际化和分发优化留给后续独立阶段。

## 目标

1. 密码记录和 TOTP 账户共用一个主密码、一个加密保险库和一个锁定会话。
2. 使用带随机盐和工作因子的密码派生算法，以及同时提供机密性和完整性保护的认证加密。
3. 保持 Java 8 编译及运行兼容性，不新增仅为保险库服务的第三方加密依赖。
4. 将持久化文件移出启动工作目录，放入当前用户的应用数据及配置目录。
5. 自动迁移现有密码库和 TOTP 数据；任何失败都不得覆盖或丢失旧数据。
6. 通过原子写入、写后解密校验和加密备份保证保险库可恢复。
7. 让密码管理器和 TOTP 面板只负责界面与交互，不再各自实现加密和持久化。
8. 为密码派生、密文篡改、迁移、锁定和文件故障建立自动化测试。

## 非目标

- 本阶段不修改密码记录和 TOTP 账户的业务字段或导入格式。
- 不接入 Windows Credential Manager、macOS Keychain、Secret Service 或云端同步。
- 不为其它工具建立通用数据库或插件系统。
- 不在本阶段拆分 K8s、数据库、画布等大型面板。
- 不把主题、语言、窗口尺寸、导航状态等非敏感设置放入保险库。
- 不承诺从已删除文件所在介质中安全擦除历史扇区；迁移只保证应用不再主动保留明文 TOTP 数据。

## 已确认的产品决策

- 密码管理器和 TOTP 共用一个主密码与一个保险库。
- 解锁任一工具后两者同时解锁；手动锁定或超时后两者同时锁定。
- 继续支持 JDK 8。
- 旧数据在首次成功验证后自动迁移，迁移前创建备份，并在新文件写入及重新解密校验成功后才清理旧位置。
- 默认空闲 5 分钟自动锁定，可选择 1、5、10 或 30 分钟，不提供永久关闭。
- 密码或动态验证码复制 30 秒后清理剪贴板，但仅在剪贴板仍是本应用写入的内容时执行。

## 方案比较

### 方案一：统一加密保险库（选定）

密码记录与 TOTP 账户存放在一个版本化密文中，共享解锁、写入、迁移和备份流程。其优点是安全边界和用户心智最清晰，修改主密码也只有一个事务。单文件故障可能同时影响两类数据，因此必须用原子替换、写后校验及备份降低风险。

### 方案二：两个加密文件，共享解锁会话

两个工具分别保存密文，可隔离单文件故障，但需要同步两套事务、迁移、密钥轮换和错误状态。修改主密码时还会形成跨文件事务，复杂度和失败组合明显增加，不适合当前规模。

### 方案三：操作系统钥匙串

系统钥匙串可以减少主密码输入，但各平台 API、安装和备份行为不同，会破坏当前便携式 Java 应用的交付方式，也不符合本阶段保持 JDK 8 和最少依赖的约束。

## 组件与职责

### `ApplicationPaths`

集中计算配置、数据和备份目录，不包含任何业务逻辑。

- Windows：优先使用 `%APPDATA%\JavaToolbox`，环境变量不可用时回退到 `${user.home}\.java-toolbox`。
- macOS：使用 `${user.home}/Library/Application Support/JavaToolbox`。
- Linux 及其它 Unix：数据优先使用 `$XDG_DATA_HOME/java-toolbox`，否则使用 `${user.home}/.local/share/java-toolbox`；配置优先使用 `$XDG_CONFIG_HOME/java-toolbox`，否则使用 `${user.home}/.config/java-toolbox`。
- 所有目录都通过 `Path` 返回；创建失败时抛出明确异常，不静默回退到工作目录。

### `VaultCrypto`

只负责密码派生、AES-GCM 加解密、随机数生成和敏感数组清理，不读取文件、不解析业务模型、不操作 Swing。

- KDF：`PBKDF2WithHmacSHA256`，新文件使用 600,000 次迭代。
- 盐：每次创建保险库或修改主密码生成 16 字节随机盐。
- 密钥：派生 128 位 AES 密钥，以兼容仍启用旧版 JDK 8 limited cryptographic policy 的运行环境。
- 加密：`AES/GCM/NoPadding`，每次保存生成 12 字节随机 nonce，认证标签长度为 128 位。
- 随机源：`SecureRandom`，不指定具体 JCA Provider。
- 不提供 PBKDF2-HMAC-SHA1、AES-CBC 或明文回退。如果所需算法不可用，保险库保持只读失败状态。
- 主密码始终以 `char[]` 传入，不转换为 `String`；派生完成后由调用方和加密组件在 `finally` 中清零暂存数组。

### `VaultEnvelope`

保险库外层是非敏感的 JSON 信封，字段固定为：

- `format`: `java-toolbox-vault`
- `formatVersion`: 初始值 `1`
- `kdfAlgorithm`: `PBKDF2WithHmacSHA256`
- `iterations`: `600000`
- `salt`: Base64 编码的 16 字节盐
- `cipherAlgorithm`: `AES/GCM/NoPadding`
- `nonce`: Base64 编码的 12 字节 nonce
- `ciphertext`: Base64 编码的密文及 GCM 标签

除 `ciphertext` 外的安全相关字段按固定顺序编码为 AAD，因此格式版本、迭代次数、盐、算法和 nonce 的任何修改都会导致认证失败。读取时拒绝未知格式、未知算法、非法 Base64、错误长度、低于 100,000 或高于 5,000,000 的迭代次数，以及超过 16 MiB 的保险库文件。新写入文件始终使用 600,000 次迭代；将来提高工作因子时可在成功解锁后重写信封。

### `VaultData`

AES-GCM 密文中的 JSON 数据包含：

- `schemaVersion`: 初始值 `1`
- `passwordAccounts`: 现有密码记录数组
- `totpAccounts`: 现有 TOTP 账户数组，包括每账户显示偏好

主密码、派生密钥、空闲时间和全局界面设置不进入 `VaultData`。模型提供深拷贝能力，面板不能持有仓库内部的可变集合。

### `VaultRepository`

负责信封序列化、文件大小检查、临时写入、写后校验、备份和原子替换。正式文件名为 `toolbox-vault.json.enc`。

保存流程固定为：

1. 在数据目录生成同目录临时文件，使用新的 nonce 加密并写入。
2. 通过 `FileChannel.force(true)` 尽力把内容刷新到存储介质。
3. 从临时文件重新读取并解密，校验 `schemaVersion` 及必要集合。
4. 如果正式文件存在，先将其复制为带时间戳的加密备份。
5. 优先使用 `ATOMIC_MOVE` 替换正式文件；文件系统不支持时退回同目录 `REPLACE_EXISTING`。
6. 替换后再次确认正式文件可读取；失败时保留最近备份并返回可恢复错误。

同一进程内所有读写由单线程执行器串行化。重复点击保存不会并行写文件，应用退出时会等待正在进行的持久化事务结束或报告失败。

### `VaultService`

作为密码管理器和 TOTP 的唯一入口，负责：

- 创建、解锁、锁定和修改主密码。
- 保存 `VaultData`，并在成功后向监听器发布状态变更。
- 维护派生密钥和最后活动时间，但不缓存原始主密码。
- 维护 `LOCKED`、`MIGRATION_REQUIRED`、`UNLOCKING`、`UNLOCKED`、`SAVING` 和 `ERROR_READ_ONLY` 状态。
- 通过 `VaultListener` 通知两个面板；Swing 监听回调统一切换到 EDT。监听事件不携带敏感数据，密码管理器和 TOTP 分别通过受限访问器取得各自的不可变数据切片。
- 由可替换的时钟和调度器执行空闲锁定，方便确定性测试。

密码管理器和 TOTP 面板在敏感读取、编辑、复制、工具切换和明确的用户输入时调用 `touch()`。仅由 TOTP 刷新定时器产生的周期计算不视为用户活动。

### `LegacyVaultMigrator`

只读取旧文件并生成 `VaultData`，不直接覆盖正式保险库。它支持四种确定场景：

1. 两类旧数据都不存在：在任一工具首次使用时创建新的空保险库。
2. 只有旧密码库：验证旧主密码后迁移密码记录。
3. 只有 `totp.accounts`：要求创建新主密码后迁移 TOTP 账户。
4. 两类旧数据都存在：使用旧密码库主密码，合并两类记录。

当新保险库已经存在时，迁移器不再自动导入旧数据，避免重复记录；残留旧文件只进入迁移收尾流程，在保险库解锁并确认其数据有效后提示重试配置迁移或旧文件清理。

### `SecureClipboard`

封装敏感内容复制。复制时记录本次写入的内容摘要并启动 30 秒计时；计时到期后重新读取剪贴板，只有内容仍与本次写入一致时才清空。该组件不记录或输出原文，剪贴板暂时不可用时只提示用户，不影响保险库数据。

## 配置迁移

`ConfigManager` 改为通过 `ApplicationPaths` 访问用户配置目录，并使用与仓库相同的临时写入和同目录替换原则。启动时，如果新配置不存在而工作目录存在旧配置，则读取旧配置并迁移所有非敏感设置。

包含 TOTP Secret 的原始配置字节和旧密码库字节作为不透明数据，分别写入使用新主密码及独立盐、nonce 加密的时间戳备份信封。备份解密校验成功、新保险库验证成功、去除 `totp.accounts` 的新配置保存成功后，才删除工作目录中的旧文件。应用不创建包含 TOTP Secret 的明文 `.bak` 文件。

备份目录只由本应用创建和读取。平台支持 POSIX 权限时，目录限制为当前用户可读写；Windows 依赖当前用户应用数据目录的访问控制。权限收紧失败会产生警告，但不会把文件回退到工作目录。

## 解锁、锁定与修改主密码

### 创建和解锁

- 创建保险库时要求输入并确认主密码，空密码被拒绝；本阶段不强制复杂度规则，只显示强度提示。
- 解锁操作和 PBKDF2 在后台执行，界面禁用重复提交并显示进度状态。
- 成功解锁任一工具后，密码管理器和 TOTP 同时收到 `UNLOCKED` 状态及数据快照。
- 错误密码、认证标签失败和无法解析的密文对普通用户显示统一的“主密码错误或保险库已损坏”，不透露可用于判断密文内容的细节。

### 自动和手动锁定

- 默认连续 5 分钟无用户活动自动锁定；可选值为 1、5、10 或 30 分钟。
- 两个面板均提供“锁定保险库”，触发同一个 `VaultService.lock()`。
- 锁定立即停止敏感编辑、清空派生密钥字节数组、释放数据快照和编辑缓冲，并通知两个面板显示锁定卡片。
- Java `String` 无法可靠覆写；密码、用户名和 TOTP Secret 等业务字符串通过释放整个快照减少驻留时间。原始主密码不得存入 `String` 或对象字段。
- 应用关闭时调用锁定，不把会话密钥写入磁盘。

### 修改主密码

已解锁用户输入并确认新主密码后，服务生成新盐和新派生密钥，以新 nonce 重写整个保险库。新文件写后校验和原子替换成功前，旧保险库和当前会话保持有效；成功后清零旧密钥并切换到新密钥。修改失败不会改变当前主密码或数据文件。

## 数据迁移事务

迁移按以下固定顺序执行：

1. 探测新保险库、旧密码库和旧配置，不写文件。
2. 根据旧数据组合验证旧主密码或创建新主密码。
3. 解析旧密码记录和 TOTP 账户，保留原有 ID、字段及顺序。
4. 为两个旧源创建强加密的时间戳备份，并逐一重新解密校验。
5. 生成合并的 `VaultData`，写临时保险库并重新解密校验记录数量和必要字段。
6. 原子安装正式保险库，并重新打开正式文件使用新主密码验证。
7. 将非敏感配置写入新配置目录，确保其中不存在 `totp.accounts`。
8. 重新读取新配置，确认必要偏好可解析且不存在 TOTP 数据。
9. 删除工作目录中的旧密码库和包含 Secret 的旧配置。
10. 发布 `UNLOCKED` 状态，并在配置中记录迁移完成的格式版本。

步骤 1 至 8 任一步失败时不删除旧源，临时文件被清理，已生成的强加密备份可以保留。如果步骤 6 已成功而后续配置迁移失败，新保险库成为权威数据源，下次解锁后只重试配置迁移和旧文件清理，绝不再次导入旧记录。步骤 9 删除失败时迁移仍视为完成，但界面必须警告用户残留文件的完整路径并提供重试清理操作。

## 错误处理与安全边界

- 密码错误、认证失败、未知版本、算法不可用、文件过大、路径不可写和 JSON 损坏使用不同的内部异常类型；界面按是否可重试给出操作建议。
- 未知保险库格式或版本进入 `ERROR_READ_ONLY`，不尝试降级解析或覆盖。
- 任何写入失败都保留当前有效正式文件，不用空数据覆盖。
- 日志和异常文本不得包含主密码、派生密钥、账号密码、TOTP Secret、完整 `otpauth` URL、完整密文或剪贴板内容。
- 账号密码和 TOTP 的增删改必须通过 `VaultService` 的串行保存事务；保存失败时面板恢复到最近一次已持久化快照，并明确提示用户。
- PBKDF2、迁移和文件读写不在 Swing EDT 上执行；所有 Swing 组件变更必须在 EDT 上执行。
- 进程间并发写不在本阶段支持。仓库通过 `FileChannel.tryLock()` 持有同目录锁文件的操作系统文件锁；检测到另一活跃进程时以只读方式打开，避免两个应用实例相互覆盖。仅存在但未被锁定的陈旧锁文件不会阻止启动。

## 界面行为

- 密码管理器和 TOTP 都根据同一个服务状态显示“首次设置”“需要迁移”“正在解锁”“已解锁”“只读错误”或“已锁定”。
- 迁移界面说明将合并哪些旧数据、备份位置以及失败不会删除旧文件。
- 自动锁定超时设置放在两个工具都可访问的保险库设置对话框中，修改后写入普通配置。
- 迁移、解锁、保存和修改主密码期间禁用会触发第二个事务的按钮。
- 错误对话框提供简短原因和可执行的下一步；涉及残留旧文件时显示完整路径，但不展示其内容。

## 测试策略

实现采用测试先行：每个行为先加入会失败的自动化测试，再编写最小生产代码使其通过。

### `VaultCryptoTest`

- 固定 PBKDF2 测试向量在 JDK 8 和当前开发 JDK 上结果一致。
- 新文件使用 16 字节盐、12 字节 nonce、128 位密钥和 128 位 GCM 标签。
- 相同数据和密码连续加密得到不同盐或 nonce 及不同密文。
- 正确密码可往返，错误密码失败。
- 修改密文、AAD 字段、格式版本、盐、nonce 或迭代次数都会失败。
- 非法长度、过低或过高迭代次数在执行昂贵计算前被拒绝。
- 测试可观察的主密码和派生密钥暂存数组在成功与异常路径都被清零。

### `VaultRepositoryTest`

- 保存后可以重新读取同一数据。
- 临时文件完成写后解密校验才替换正式文件。
- 模拟序列化、刷新、校验、备份和移动失败时，原正式文件保持可读。
- 不支持 `ATOMIC_MOVE` 时同目录替换路径可工作。
- 超过 16 MiB、损坏和未知版本文件被拒绝且不被覆盖。
- 并发保存被串行化，第二进程锁导致只读状态。

### `LegacyVaultMigratorTest`

- 覆盖无旧数据、仅密码库、仅 TOTP、两者都有四种场景。
- 旧密码错误、旧密文损坏、TOTP JSON 损坏、备份失败和配置写入失败都保留旧文件。
- 迁移保留记录 ID、字段、顺序和每账户 TOTP 显示偏好。
- 正式保险库存在时不会重复导入旧记录。
- 成功迁移后的新配置不包含 `totp.accounts` 或任何 TOTP Secret。
- 原始旧文件只在正式保险库重新解密成功后删除；删除失败产生可重试警告。

### `VaultServiceTest`

- 从任一入口解锁后两个监听器都收到一致状态；两个面板只能取得各自的数据切片。
- 手动锁定、空闲超时和应用关闭会清理会话并通知所有监听器。
- 使用可控时钟验证 1、5、10、30 分钟设置及 `touch()` 行为。
- 修改主密码成功后旧密码失效、新密码可解锁；写入失败时旧密码继续有效。
- 增删改保存失败时恢复最近已持久化快照。
- 重复解锁、保存或迁移请求不会创建并发事务。

### Swing 与剪贴板测试

- 两个面板始终呈现一致的锁定、迁移和错误状态。
- PBKDF2 和文件操作不阻塞 EDT，监听回调在 EDT 执行。
- 敏感内容 30 秒后在内容未变化时清空；用户随后复制其它内容时不清空。
- 锁定后所有敏感编辑入口不可用，重新解锁后从仓库快照恢复。

### 回归和兼容性验证

- 运行现有完整 Maven 测试套件。
- 在 JDK 8 和当前开发 JDK 上运行测试与打包。
- 使用临时用户目录执行迁移集成测试，不读取开发者真实配置或保险库。
- 人工验证四种迁移场景、错误密码、损坏文件、自动锁定和修改主密码。

## 验收标准

1. 普通配置和工作目录中不再保存 TOTP Secret。
2. 新保险库使用 PBKDF2-HMAC-SHA256、随机盐和 AES-GCM，任何受保护元数据或密文篡改都能被检测。
3. 密码管理器和 TOTP 共用解锁、手动锁定和空闲锁定状态。
4. 旧密码记录和 TOTP 账户在支持的四种场景下无损迁移。
5. 迁移或保存失败不会删除或覆盖最后一个有效数据源。
6. 新配置和保险库位于用户应用目录，不依赖启动工作目录。
7. 主密码不以 `String` 或磁盘字段保存，会话密钥在锁定时清零。
8. 剪贴板在内容未被用户替换的情况下于 30 秒后清理。
9. 所有新增测试、现有测试及 JDK 8 和当前开发 JDK 打包均通过。
